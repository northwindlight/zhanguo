2026-11-24。用户确认同一四国局由 A/B 两组权重各控制两席，轮换席位；模型逐动作重新观测时，要保留 legacy 的“提交建设后立即占位”观测。

## main 的实际边界

已 fetch 并核对 main/origin/main：`72724fd7a3b214ab6690b09d5e1141dae5869da1`。main 本轮未改。

- `engine/session.py:546` 按冲突边的连通分量分组，组内沿轮换顺序执行，组间并发。纯 AI 局需要显式 `planning_workers>1`，默认串行。
- `mods/native/army/domain_objects.py:252` 用当前位置、移动/攻击可达范围及已有军令目标形成行动包络；按周期缓存，包络相交即产生冲突边。它不是简单按宣战名单分组。
- 世界读写由会话锁保护；推理/客户端等待在锁外。`Session.cycle()` 等行动期结束后调用一次 `before_settlement()` 和一次世界结算。
- `NativeSession.before_settlement()` 按轮换次序推进建造、征兵、自动交易与外交收尾。`end_turn` 不触发单国清算。
- 市场报价在期内固定，大单冲击按 `(owner, side, resource)` 累计；总库存与下期报价在期末清算，符合经济行动并发的前提。
- 准确时序：建筑/征兵提交时立即预付并预占，期末开工/出兵。交易、移动、进攻、拆除等仍有即时世界变化，不能把所有动作都视作纯排队。

现有 C++ `Episode::advance()` 仍逐国推进，每世界只有一个 `seat`。`Slot` 已有四席各自的 GRU 隐状态和轨迹，适合作为改造基础。

## 确定的双卡方案

每个世界四国共享真实市场和战场。A 在 GPU0、B 在 GPU1，各控制两席；两组各自保留策略、价值头、Adam 状态和采样快照。各国保持独立库存、视野和 GRU 隐状态，外交仍由规则决定。

按 `seed % 6` 轮换六种席位分配：AABB、ABAB、ABBA、BAAB、BABA、BBAA。六图内每个位置各有三次归 A、三次归 B。每个世界只计一次训练局数；2000 世界合计 8000 国家轨迹，其中 A/B 各 4000 条。

一批采样期间固定 `(A_k, B_k)`，候选的观测、动作索引、logp、value、国家历史和 GDP 都绑定对应策略版本。采完后，各卡只用本组两席的轨迹做 PPO。优势归一化、GRU 回放、价值目标和优化器也分别计算。A/B 都更新完成后，再提交 `(A_k+1, B_k+1)`，供下一批使用；不做权重平均或梯度同步。

每批双检查点要作为一个事务提交：先保存并核实 A/B 两份权重、优化器及 SHA，再发布同一个 manifest。任一组失败，保留上一对已提交快照，不能把半批新权重投入下一局。

独立更新后，aggregate samples/sec 与“同一个策略的更新速度”是两种指标，不能直接宣称同一策略快了两倍。每组训练数据减半，`subsample=.25` 与 `max-batches=384` 的实际更新次数也会变化，实测要同时报告两组样本数和更新数。

## 动态采样的接口改造

1. `Episode` 提供显式 `observe(actor)` / `act(actor, candidate)`，按 main 的冲突组维护每组当前可行动国家；结束一国只推进该组，全部组结束且无未返回请求后才统一结算。
2. 推理请求独立携带 `(world, actor, period, policy_version, observation, candidates, memory_key)`。同一国家只保留一个未完成请求。请求持有所用观测及候选，执行时按原动作参数重验，不能拿旧索引访问新候选列表。
3. GPU0 汇总所有世界中属于 A 的就绪国家，GPU1 汇总 B。请求不足目标批量时及时发送，不能等到所有四国都有资格才推理；冲突组必须允许只有一国就绪。
4. CPU 协调器串行提交同一世界的动作，GPU 工作线程只推理；观测准备可跨世界并行。同一世界的可达、外交和视野缓存存在可变状态，不可直接把多个国家塞进现有跨世界 OpenMP 循环而不加保护。
5. GRU 每国每回合只前进一步，本回合所有动作共享该隐状态。训练仍回放所选国家的完整因果历史，不能把拆出来的任意回合当成全新零隐状态，也不能混进另一国家的历史。

当前每卡四世界、每世界单就绪国家，所以推理批次约四条。接入动态回合后，无军队冲突时每世界最多四条就绪请求，八世界的 A/B 各最多十六条；这是就绪数量上限，不是吞吐倍数承诺。CPU 观测开销、padding、战争冲突和显存仍会限制收益。

## legacy 观测兼容

正式状态与已提交订单是唯一数据源。每次观测重建只读投影，避免以一次动作回执为依据长期保留已取消或失地的“幽灵建筑”。

| 模型看到的内容 | 取值口径 |
| --- | --- |
| 可用库存 | main 提交预付后的真实余额，不再次扣费 |
| 已落成建筑 | `instances` 中 `remaining==0`，可贡献真实生产/电力/防御 |
| 待建/在建数量 | 未落成实例，加本国已接受但未开工订单；同一个 id 只计一次 |
| 建筑位、资源容量 | 使用正式 `site_capacity`，它已包含队列预占 |
| 旧 tile 的 pending 通道 | 表示上述待建数量，不把它加进“已落成”通道 |
| 取消、开工、失地、完工 | 下一次读正式状态重建；真实退款、开工资格与扣费仍走 main |
| GDP、供电、存亡与战斗 | 使用真实结算/世界状态；投影不赋予待建厂产出或待建城防效果 |

只改观测不够：候选里的空间、当期施工额度、资源容量、费用、退款和可执行性也必须用同一正式口径重算，避免“观测已占位，候选仍说空着”。main 允许多期队列、取消未开工全退，legacy 的单期施工和在建半退不能混用成第二套执行规则。

征兵还有额外差异：C++ legacy 立即生成本期不能行动的新兵；main 在期末生成。若保留 legacy 的军队观测形式，需另做带稳定订单身份的计划单位投影，并按实际当期能出兵的数量区分多期排队，不能让影子单位提前参与战斗/供给/包络计算。该部分尚未实现。

## 实际验证及边界

- main 原有 `tests.test_parallel_action`、`tests.test_desktop_parallel`：18 项通过。
- `probe_main.py` 在四国实际世界测试无军队、一对冲突、两对冲突、全部冲突，分别得到 4、3、2、1 个并行组；结果 `main-probe.json`。
- `verify_independent.py` 使用真实 BC 第四轮的完整 d192/xattn/cand_layers2/GRU128 权重，以及同一四国世界的八条真实观测，启动两个独立 CPU 进程各做三次 PPO 更新。A/B 轨迹无交集且覆盖四席；并发 A 与单独 A 参数完全一致；将 B 的特征/收益大幅扰动后 A 参数完全一致；A/B 更新后自然分化。结果 `independent-proof.json`。这是三回合样本上的正确性验证，不是双 T4 性能或长局策略验收。
- main `tests.test_production_queue`：18 项通过。
- `legacy_projection.py` 的六项真实 main 测试通过：提交即占位、观测不重复扣费、待建电厂不算已投产、开工不重复计数、取消释放及全退、仅本国信息且结果可独立修改。结果 `projection-proof.json`。这只是建筑投影原型，未接成完整模型编码器。

早期研究过共享权重 DDP：小模型数值验证通过，生产模型多步 FP32 与单批基线的严格数值阈值未通过；该路径不是用户最终选择，不能将 `ddp-production-proof.json` 称作通过。PyTorch 的梯度同步语义参考 [2.11 官方 DDP 文档](https://docs.pytorch.org/docs/2.11/generated/torch.nn.parallel.DistributedDataParallel.html)。当前 A/B 方案各自更新，避免了这条共享梯度链。

接入后仍须在双 T4 实测两卡采样/更新的重叠、每组吞吐、显存、CPU占用与完整一批墙钟，并以共享世界的逐动作对拍核实冲突排序和单次结算。现阶段不能据此断言双 T4 已达到单 L4 的速度。
