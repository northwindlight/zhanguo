### 模型知不知道建筑效果？**不知道，它得自己建模**（2026-09-12 核过代码）

观测里跟建筑有关的只有两处**计数**：
- 网格：每格每建筑的数量 `log1p(c)/3`（视野门控，`rl/env.py:514-521`）
- 全局：本国每建筑总数 `log1p(tot)/3`（`rl/env.py:620-626`）

`game.BUILDINGS` 那套数值（`kind`/`cost`/`wood`/`cap_resource`/`outputs`/`inputs`/`fuel`/
`energy_out`/`energy`/`limit`/`min_slots`/`limit_nation`/`max_level`）**一个字段都没进观测**；
候选也只带下标（`type_idx` + `sub_idx` + 落点 + 军队 + 数量档，见 `_cand_pack`），
不带造价与效果。而候选枚举（`rl/env.py:272-309`）**是拿这些表算过的** ——
地形惩罚、工程院折扣、匈奴加成、`cap_resource`、`min_slots`、`limit`、买不买得起，
所以「候选存在」泄露一比特（**此刻建得起且合规**），**幅度不可见**。

于是：空间相关的部分它学得到（资源类型在网格通道里，"耕地格铺农场"能从数据里出来），
但**幅度只能靠奖励（总消费增量）反推**，且是**逐个建筑、逐个下标**地拟合。
**推论**：换一种建筑、改一个造价，模型**零先验**。预留位与通用性是两件事 ——
预留位保**形状**，把规则表当**输入特征**喂进去才保**通用**。

### ★为什么「改数值就拟合不上」是**表达能力**问题，不是精度问题（用户 2026-09-12 点的）

用户原话：「这炉模型只能是版本特化的，如果我平衡调整，例如石油发电厂降价，他就拟合不上了。」

对，而且机制比"拟合不好"更硬：**`π(a|s)` 只能依赖 `s` 里有的东西**。
石油能源厂的造价（现值 `cost: 240 / wood: 15 / fuel: 石油1 / energy_out: 8`）不在观测里，
所以降价 240→180 之后，模型**在同一个盘面上给出的决策一模一样**——它看不见这个变化，
而最优决策已经变了。不是它学歪了，是**它没有可以依赖那一维的接口**。

连带效应（容易被忽略的一条）：候选枚举用的是**实时表**（`gold < cost` 才生成候选），
所以降价后**新冒出一批原先买不起的候选**。模型对这些「新出现的选项」零经验，
只能按旧的建筑先验乱选 —— 表现上像"变笨了"，实际是输入分布被劈了一刀。

**训练分布里只有一个价格点，学到的就是"这一个点的答案"**，不是「给定价格该怎么选」。
要通用，两条缺一不可：
1. **数值进输入**（每个建筑一个特征向量：造价/木耗/产出/耗电/燃料/门槛/slots）→ 函数**能**依赖它；
2. **训练时对数值做域随机化**（整表重采样或 ±% 抖动）→ 函数**见过**这条依赖，才谈得上泛化。

只做 ① 不做 ② 仍然是单点拟合（喂了数值也只见过一个值）。
观测里其实已经有先例：`prices` / `equilibrium` 每回合都在变、也在输入里，
模型**已经在**condition on 价格了 —— 把建筑造价表接上去是同一个套路。

## 二、用户已定的：**要记忆**

原话：「要记忆，没有记忆做不成长局规划」。**这条不用再论证。**

### 三条核实过的事实（别再重查）

1. **LLM 玩家有记忆，RL agent 没有。** 引擎侧 `_map_snapshot()`（所谓"已知地图"）
   算的是 `own_tiles` + `frontier_of` —— **当前**视角，不是累计记录。
   **但 LLM 的记忆不在引擎里，在它的上下文里**：它每回合读面板（`mp_ai.py:619`），
   面板留在会话历史里，百万上下文整局都在。
   → **加记忆是把这条不对称补平，不是给 agent 加特权。** 契约第 2 条不拦它。
2. **不能靠"不抹 `vis`"来实现。** `_place_crosses` 会把**各国开局的地块**都建进
   `world.tiles`（含对手的）→ 不抹的话 agent 从第 0 回合就看得见楚的起始格。
   **那是偷看，不是记忆。**（`_spawn_guardian` 不建 tile，野人没这个问题。）
   → 必须**显式记"我实际观察过什么"**。
3. **全上下文窗口不可行，理由是 token 数不是算力。**
   LLM 的前向+反向对一段数据**只做一次**；**PPO 的更新侧每轮 epoch 都要对每个存下的
   step 用新权重重算整窗**。同样机器同样训练法：窗口从 321 涨到均值 8 万 →
   **一局从 9 分钟变成 ~37 小时**（250×），而且这只是线性项的下界。

   —— batch 256 时那一个张量 **422 MB**，是我们为 P4 把 batch 降到 32 的直接原因之一。

★★**P4 的真实成本比设计文档估的低 7 倍，而且原因值得记牢**：
`TOKEN_DESIGN` §6 拿"FLOP 比 ≈42×"外推到"1 小时/局"，**那是错的**——
122k 老模型跑在 **batch 256** 上，候选要补到批内最大（K≈400），**绝大部分算力花在
padding 上**；Transformer 跑 batch 32、GEMM 更大更高效。**FLOP 比不等于秒数比。**
（模型也修正了：d192/4层实际是 **2,083,986** 参数，不是文档写的 ≈3M。）

**★P4 的瓶颈是内存，不是算力**：窗口激活 ∝ `batch × token × d_model`，batch=256 时
光**自注意力掩码** `(B,H,T,T)` 一项就是 422 MB，4 层合计把 ECS（3.7 GB）压进 swap ——
**表现是"一步几分钟"，很容易误判成算力不够**。所以 `--minibatch` 的默认值现在
**按主干定**（mlp/pool 256、tf 32），并按三项（激活/自注意力掩码/候选掩码）
打印粗估。判断是不是在换页，**看 `free -m` 的 Swap 行**，不要看 CPU。

**换 GPU 的账**：`pack` 那 51 ms 是 **GPU 加速不了的硬底**。
→ 现在这个 122k 模型：前反向 838 ms，天花板 `889/51 ≈ **17×**`（GPU 再快也就这样）。
→ P4 的 3M/512：`pack` 不变、前反向涨 ~40× → pack 占比掉到 ~0.2%，**天花板 ~50×+**。

**但换 GPU 换来的不是"更快"，是"3M/512 这条尺寸约束可以作废"** —— `TOKEN_DESIGN` §6 明说
选 3M/512 就是为了"一个月内 ECS 跑得完"。

★**2026-09-11 用户更正了这条期限**：
- **GPU 是按天租的** → 要上就上在**核心阶段**，不用为它提前改设计；
- **"一个月"不是项目的硬限制**，只是阿里云免费期。**可以租别的机器。**

→ 所以 **3M/512 不该被当成"因为只有一个月"的妥协**。它现在的正当理由只剩一条：
**P4 要答的是 yes/no（注意力+候选 cross-attn 学不学得会规则 AI 的逻辑），
小模型答得更快、迭代更多。** 等这个 yes/no 有答案、进核心阶段时，
再按那时的算力（可能已经是按天租的 GPU）重新定主干和窗口 —— **不必被今天的预算锁死**。

**建议：P4 之前不换 GPU。** 理由是"P4 要的是迭代速度不是吞吐"，
不是"来不及"（那台机器上换 GPU 会跟 P4/P5 抢时间；且 PPO 采样是 batch=1 逐步前向，
在 GPU 上延迟绑定、未必更快；env 是单智能体，不支持并行喂 GPU）。

### P1 已量到的（2026-09-11，`experiments/speed_probe.py`）

| | 采样（整局） | 梯度 / 步 | 外推 250 步 = 一局 |
|---|---|---|---|
| **ECS @1 线程**（实跑日志） | 0.7 s | **0.347 s** | **88 s** |
| Pi 5 @4 线程 | 1.0 s | 0.780 s | 197 s |
| Pi 5 @1 线程 | 1.0 s | 1.257 s | 316 s |

**三条结论：**

1. **采样只占 1~2%，梯度步占 97~98%。** 所以"本地开多线程"救不了 —— 能并行的
   那部分本来就不是瓶颈。瓶颈是 torch 小矩阵，由 **SIMD 宽度**决定
   （ECS AVX512 16 fp32/周期 vs Pi NEON 4/周期）：Pi 单线程就慢 3.6×，
   4 线程只买到 1.61×，补不回来。→ **训练放 ECS。**
2. **服务器一律单线程。** 实测 ECS 开 2 线程比 1 线程**慢 3.4×**（SMT 逻辑核
   对向量零收益，纯粹多了同步开销）。`--threads` 默认从写死的 4 改成
   **0=自动=物理核数**（`rl/hw.py`），ECS 自动得 1、Pi 自动得 4，两边都不用记着传参。
3. **bf16 在 ECS 上快 1.36×**（0.507→0.373 s/步，同负载背靠背量的**比值**可信；
   绝对值被训练进程抬高过）。**暂不开**：122k 参数的模型上省这点不值得拿
   梯度质量冒险，等 P4 的 3M 主干上再量一次（那时矩阵大、还能省一半激活内存）。

CNN、候选嵌入、点积打分、**价值头**全部原样——价值头继续吃原始 `glob`
（它有自己的理由不共用 `g`，见 `rl/model.py` 的注释）。

**故意做得很笨**：编码器里**不含任何集合级运算**（没有注意力、没有排序）。
因为 P3 的任务是**证明这条管子通了**，不是证明它强。一旦这里上了注意力，
P4 分数掉了就分不清是 tokenize 编错了还是注意力没训上来——那正是 §7 要分开的两件事。

**它不主张"效果"**（用户口径：P1/P3 只测管线）。所以 P3 的验收是：
两条路都跑得起来、不 NaN、窗口那条的编码器**确实拿到梯度**（不是 no_grad 死枝）、
掩码补零**零泄漏**（`tests/test_window_head.py` 10 条）。
"窗口路和 glob 路谁更准"**不是 P3 的问题**——那是 P4 的事。

## 部署与运行

```bash
# 从 Pi 推代码（ECS 上 GitHub 不通，只能这么走）
~/bin/deploy-zhanguo-ecs          # = rsync，明确排除明文凭据/rl/runs/；连不上会报错

# 在 ECS 上跑：**一律走 rl/run_ecs.sh**（它把线程钉死为 1 + 起 tmux + 落日志）
ssh northwind@ecs.northwind.site
cd ~/zhanguo
./rl/run_ecs.sh bc --teacher v9 --episodes 40 --dagger-from 20 --turns 70 \
    --ckpt-every 4 --out rl/runs/bc/v9_70.pt
./rl/run_ecs.sh status        # 看任务
./rl/run_ecs.sh logs          # attach
./rl/run_ecs.sh kill          # 停
```

`run_ecs.sh` 管的三件事，都是踩过的坑：**① 线程全钉 1**（`OMP_NUM_THREADS` 等
必须在 import torch **之前**设，所以只能写在启动脚本里；ECS 开 2 线程慢 3.4×）；
**② 必须 tmux**（Windows 机上 ssh 会话一断进程就被带走，丢过一次）；
**③ 拒绝重复启动**（`status` 里发现同名 tmux 会话直接报错退出，不允许同时跑两个训练）。
