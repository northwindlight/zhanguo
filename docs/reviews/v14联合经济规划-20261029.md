# v14联合经济规划：实现与验证

用户要求改进经济层并准备v14，随后明确采用运筹学联合规划。实现采用SciPy1.15.3／HiGHS混合整数求解；原顺序评分原型已替代，不将其旧样本成绩列为本版结果。v14为可选候选，默认仍为v13；综合验证通过后再晋级，旧档继续记录的策略版本。游戏包对应0.7.1，规则AI版本对应v14。

## 实现范围

`ruleai/v14/inputs.py`只收集绑定玩家可读的事实；`joint.py`构造跨地块／跨期整数模型；`linear.py`调用真实求解器并独立检查变量界、整数性和约束；`economy.py`在正式报价验资后提交首期，`entry.py`保留原军事控制器。数学结构与限制见[设计](../design/v14联合经济规划.md)和[策略说明](../../ruleai/v14/README.md)。

- 基础时域4期，包含已知原生贷款的近期到期；建设前置、每格施工额度、空间与资源共享位、工程院折扣和预付队列全部进入约束。不开动人工队列、不重复支付。
- 采集、发电、工业、市政厅按正式顺序核算，生产不得自由关闭，缺电全网停工；新建筑下一期才生产。贡赋小数和银行还款使用正式读取口径。
- 补给必须按需求与库存的最小值自动扣取，恢复使用整数装备，断粮停止恢复。没有通过虚构少吃、少恢复留下库存。
- 先求一个本期联合运营方案，取得已知可达的服务水平，作为长期模型硬上限；不能因受限搜索而接受更差的本期缺口。长模型无可行解时执行一期运营，不退回逐项评分或逐资源采购。
- 各层8节点／5秒，经济层目标2%间隙（预算耗尽时实际间隙可更大）；区分最优、容差、受限与之前阶段的可行解。没有证明最优时不冒称最优。墙钟上限意味着不同算力／负载可能取得不同可行方案。

目录增加只读生产阶段、规划增加正式工程院后报价、银行提供按当前利率的到期预估，未改变世界状态或模块依赖版本。原v13／v11plus代码及存档语义保留。真人经济入口与扩军可分开，但没有接入GUI托管。

新增军费预算按模型中实际可运行的净产出计算，保留原30%比例而不靠旧满负荷快照判断；扩军请求保存绝对期限，避免每次重算都顺延。未来价格用现价与公开预测的保守区间，期末库存按整单深度清算，不把库存乘边际价或预测涨价当作确定收益。

## 核对与交付

专项核对包括小模型完全枚举、当前／未来库存守恒、新电厂生效时点、全网断电、工厂共享原料、工程院跨期价格、自动供粮与恢复、贡赋余数、银行还款、已知期限扩窗、行动预算、受限求解恢复和版本化续档。本机最终全量离线回归1100项通过（2项环境相关跳过），提前加载修复后39项策略／纯源码打包专项通过；C#构建、布局、API参考与文档链接检查通过。合并提交由CI重新执行完整离线回归及Windows便携包实际窗口检查，最终结果见文末。

本机C#构建与布局检查通过；Godot .NET在Xvfb／Mesa llvmpipe打开实际菜单，并验证看海／玩家新局表单生成v14配置。此项不代表Windows显卡或Vulkan性能。Windows NumPy／SciPy轮子经SHA-256核对并实际安装到打包目录，许可证完整，移除构建机路径相关启动器；内置解释器的真实求解能力仍由Windows包验收覆盖。

固定画面的演出／灭国／银行夹具显式使用原v13输入，避免默认策略变化污染视觉案例；独立的便携求解器检查显式要求八国v14，并通过随包Python完成完整回合，因此不会用旧策略替代新求解器验收。

## 对照口径

`experiments/rule_market/run.py`离线生成24×24八国合成局，不读取真实对局。固定土地模式仅屏蔽移动／攻击，保留扩军与军需；完整模式保留原军事控制器。统计正式生产记录的投入／产出，使用开局固定中间价估计实际生产净值，同时报告军需、行动失败、计划拒交与求解状态。

净产出不含建材、征兵／维护和交易成本，不是全口径利润或胜率。所有现金、建筑和军队数字均为八国合计，初始金币合计12000。实际断粮读取已结军需回执，`next_preview_short_nations`只是期末库存对下一次补给的静态预演，不能据此声称本期已经饿兵。生产`missing-input`包含规划有意不投料的产线，也可能反映闲置产能，不能一概当成功或故障。

后续继续检验长期市场反馈、闲置产线、不同初始资源与混合对手。未来价格尚未精确包含所有新产能对长期市场的非线性反作用；当前样本不能证明无限时域最大复利或完整战争优势。

纯经济样本净产出提高29.9%，带扩军样本降低17.2%。两模式四组均无失败行动、无整套方案拒交、无实际断粮，停电仅各国首期原有市政厅的8次；这不代表已消除闲置产能，v14两组分别仍有349／546条`missing-input`生产记录。

v14纯经济160次规划中9次使用一期运营恢复，综合组全部使用长期模型。受限解仍存在，最大经济间隙分别约13.6%／75.6%，不能把2%目标当作每次保证。求解明显慢于v13，数值和耗时也可能受墙钟上限及机器负载影响。

因此本次只合并可选候选，不切换默认。下一步应继续联合优化扩军需求、资本周转与长期产能的目标权衡，并增加混合对手与长局检验；不能用纯经济的提升掩盖综合开局退步，也不能从20期样本推断长期利润或胜率。

Windows交付核对：最初两次便携检查分别超过90／300秒，预发布均未创建；同样的八国Python协议在本机约30秒完成。随后固定HiGHS与桌面宿主BLAS线程、限制纯IO验收的空转帧率，并加入独立的内置Python数值DLL探针、求解起止及线程诊断，继续由Windows CI验证，不将Linux通过冒充Windows通过。

第三次[Windows验收](https://github.com/northwindlight/zhanguo/actions/runs/40909634102)中，独立内置Python探针正确解出整数最优值25，但桌面宿主在第一次`import numpy`加载`_multiarray_umath`时阻塞，尚未进入HiGHS；后台线程同时读取管道stdin。现场与[NumPy上游问题24290](https://github.com/numpy/numpy/issues/24290)一致，不能解释为模型求解耗时。修正为实例化v14客户端时加载所需数值DLL，早于桌面和终端宿主启动输入线程；仅导入策略注册表／选择v13仍不加载数值库。仍由同一八国v14完整回合检查验证Windows修复。
