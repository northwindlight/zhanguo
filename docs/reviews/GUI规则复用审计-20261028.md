# GUI 规则复用审计

2026-10-28，基于 `e838571`。用户澄清：反馈是合法可达目标被 GUI 判成不可达，范围不限于动画；要求任何增删先查引擎，优先使用已有 API 的语义。本次仅审计和记录计划，没有修改游戏或发布新版本。

2026-10-29状态：下文为历史审计。军令三类误拦截与逐格导航已在v0.6.3收敛；v0.7将防御数值和自动交易预验复用领域纯规则，删除相应C#规则片段，见[银行邮箱与规则收尾](银行邮箱与规则收尾-20261029.md)。本清单内六处已处理，不代表对全库所有派生显示作零重复承诺。

## 已复现的误拦截

使用正式运行时和测试夹具创建两个独立合成局，不读私人存档，不调用模型。结果见[复现数据](gui-rule-reuse-cases-20261028.json)。

1. **敌国地块上另有中立第三国正在进攻。** 秦与楚交战，赵也在进攻楚，但秦赵互相中立。楚的可见地块上有楚守军和交战中的赵军。规则公开 `reachable(attack=true)` 包含此格，正式 `PlayerSession.submit(military, attack)` 成功并进入交战；`HumanAPI.targets()` 却排除此格，`HumanAPI.submit()` 报“当前已知状态下没有军队可执行此目标”。

   原因是 [candidates.py](../../mods/native/army/candidates.py#L70) 对第三方交战的过滤缺少“无主地”限定，而引擎 [Military._batch](../../mods/native/army/domain_objects.py#L286) 只在无主地处理这种抢战限制。即使目标完整可见，两个判断也不一致。

2. **移动后原地进攻已清空守军的无主格。** 正式 API 允许原地攻击并占领，真人候选也保留此目标；C# 按钮使用 `未新募 && (未移动 || 现场有外国军队)` 判断可否攻击，已移动且现场无外国军队时会置灰，漏掉原地攻击例外。

   此例实际调用了正式军令 API；按钮结果按 [SelectionChanged](../../mods/ui/desktop/Scripts/Desktop.Human.Panels.cs#L129) 的相同表达式复算，未启动 Godot 窗口，不能称为真实窗口点击复现。

这是两个合成反例，足以证明 GUI 路径存在语义误拦截；尚未取得用户遇到的具体对局，不能断言这两例涵盖全部反馈。

## 明确重复：4 类、至少 6 处规则片段

范围为真人军令、建设征兵、市场和地图数值显示的调用链。按独立规则判断片段计数，同一函数被多次调用不增加处数；不是全库重复代码的精确总数。

| 规则类别 | 重复位置 | 已有引擎语义 | 影响 |
| --- | --- | --- | --- |
| 可达、地形代价、通行和攻击目标：1处 | [army/candidates.py](../../mods/native/army/candidates.py#L51) 自行搜索并过滤目标 | `native:army.reachable`、军队领域 `reachable` 与执行校验 | 已复现合法可见目标被排除；用于提交前拦截时会阻止正式 API 执行 |
| 军令行动资格：3处 | [候选中的行动限制](../../mods/native/army/candidates.py#L38)、[按钮 SelectionChanged](../../mods/ui/desktop/Scripts/Desktop.Human.Panels.cs#L129)、[UnitReason 与可行动筛选](../../mods/ui/desktop/Scripts/Desktop.Human.Panels.cs#L164) | 军队 `action_reason`、`reachable_many` 的状态与原地攻击例外、`can_disband`、撤退校验 | 新兵、已移动、交战、被进攻及原地攻击的语义有多份；已复现按钮误禁用 |
| 自动交易参数：1处 | [FillAutoTrade.Validate](../../mods/ui/desktop/Scripts/Desktop.Human.Market.cs#L220) 再判断买入目标不高于卖出目标 | `native:market` 的 `_validate_rule`、公开 `auto_trade` 提交 | 当前同义，尚未发现本项反例；后续规则调整有两处需同步 |
| 战斗防御显示：1处 | [SquadView.Summarize](../../mods/ui/desktop/Scripts/SquadView.cs#L34) 自判攻守并再算地形与城堡合成防御 | 军队 `defense_pct`、公开 `battle` 的攻守／`combined_reduction` | 当前公式同义，但显示层保存了独立公式与攻守判定；尚未证明本项数值错误 |

“GUI路径”包含 Python 真人应用适配层；`candidates.py` 虽在 `mods/native/army/`，由真人接口调用且不复用实际军令路径计算，因此仍纳入本次审计。

同一候选算法还被 `HumanAPI.submit()` 再调用作为硬性提交门槛。这是同一实现的第二个拦截点，不另计为一套算法。C# 地图点击要求候选圈内有目标，之后 Python 再过滤，最后才会到引擎。

## 其他本地衍生判断与已复用的部分

下面这些未计入上述6处，也不能一概视为规则错误：

- 征兵入口的 [HasRecruitFacility](../../mods/ui/desktop/Scripts/Desktop.Human.Inventory.cs#L9) 从建筑角色和落成状态判断是否展示入口。正式征兵资格已有 `native:army.planning`；需核对入口筛选是否会把本应可检查或操作的地块隐藏。
- [HumanAPI.market_options](../../mods/native/human.py#L93) 使用正式整单报价，再比较本国金币／库存来置灰；没有重写市场深度和成交价格算法。`trade_quote` 本身不返回完整的钱包可成交状态，不能未经核对就声称已有完全等价的市场可用性接口。
- [desktop_catalog.present](../../mods/ui/desktop_catalog.py#L34) 在正式报价／收益估算上再算投入估值、回本期和电力提醒。这些影响显示，当前不阻止建设；仍须核对现有经济预演结果，防止把额定／预计值写成实际限制。
- 名称翻译、列表排序、按用户条件筛选、血量求和、窗口布局、输入队列和演出暂停属于呈现或交互职责，不因有计算就算重复规则。

建设和征兵的实际候选、价格、地形加价、资源余额与额度，已通过 `HumanAPI.site_options()` 调用引擎 `native:buildings.planning`、`native:army.planning`；C# 主要读取返回的 `available / requirements / price`。拆除也已读正式拆除候选和退款结果。市场整单价格调用 `trade_quote`；贷款预览调用正式 `quote(borrow)`，报表读取正式 `report`，未在本次范围中发现另写完整定价、授信或报表规则的实现。

## 下一轮收口依据

先逐项核对已有玩家 API、规划／报价、目录和执行回执，再确定需要删除的 GUI 自算与真实接口缺口。已有语义直接透传，图标、候选、置灰和正式提交保持同一规则依据。

公开 `reachable` 的单支返回值目前只有目的地，批量结果才保留逐支行动状态；`retreat` 也不等同于 `reachable(attack=false)`。应先核对和保留已有领域语义，不能机械替换后再在 GUI 补新规则。迷雾尝试仍须标明不确定，并遵守玩家信息权限。
