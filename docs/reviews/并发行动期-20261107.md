# 并发行动期（2026-11-07）

实现性质：引擎调度层，动态回合的 M0（并发等待）。默认不改变任何既有行为；`planning_workers > 1` 才启用。

## 做了什么

- `engine/session.py` 抽出 `_play_actor()`（单国完整行动循环）与 `_cycle_parallel()`：
  - 并发时用 `ThreadPoolExecutor` 同时跑各国客户端（LLM 网络等待、规则 AI 规划、脚本客户端）；
  - **世界写入仍由 `session.lock` 逐条串行入账**，不并发改世界；单条命令仍是原子的；
  - 回执按 `turn_order()` 归并，`last_results` 与串行同序；
  - `before_actor()`（自动军令推进等）在并发开始前先串行执行一遍；
  - 回调（`emit/head/on_call/on_stream`）加锁串行，避免多个客户端输出行交织；`on_result` 本就在会话锁内调用；
  - 结算仍只调用一次 `resolve_turn()`，18 阶段与存档边界不变。
- 配置：`planning_workers`（顶部配置，默认 1）。`>1` 且无真人、无 `on_batch` 演出背压时启用并发；否则自动退回串行（真人输入与演出确认由主线程驱动，在工作线程里等待会死锁）。
- `tests/test_parallel_action.py` 五个用例：默认串行、并发确实重叠等待且回执按行动顺序归并、演出背压回退串行、并发周期可审计/可保存、配置校验。

## 没有做（明确边界）

- **真人 GUI 并发**：桌面宿主带 `on_batch`/`on_human`，当前一律串行；多 actor 演出队列与真人等待并行是后续工作。
- **战争有序**：本轮所有可行动国家同时等待，不按战争图分组、不设组内顺序；这是 M1。
- **观察时序**：并发期间一个国家的客户端可以读到其他国家刚提交的动作结果（实时世界）；"看到别人正在行动"的语义与证据要求尚未定义，M1 再定。
- **确定性**：写入顺序取决于线程抢锁顺序；审计是正典（可回放），但同一计划不保证在并发下复现同一结局。M1 若要确定性写序，需要写入令牌/提交序号。
- 自动交易仍在各自 `end_turn` 时执行；市场库存清算在结算阶段。

## 验证

- 全量 `python -m unittest discover -s tests -q`：1105 项通过、17 项跳过（新增 5 项并发用例）。
- 默认 `planning_workers=1` 时行为与原串行逐行同构（独立函数抽出，回执、回调、结算顺序不变）。
- 并发用例实测：三国、workers=2、客户端等待 0.25/0.05/0.05 秒 → 同时最多 2 个客户端在跑，墙钟明显短于串行之和，回执仍按行动顺序归并。
