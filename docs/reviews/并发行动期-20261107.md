# 并发行动期（2026-11-07）

实现性质：引擎调度层，动态回合的 M0（并发等待）。默认不改变任何既有行为；`planning_workers > 1` 才启用。

## 做了什么

- `engine/session.py` 抽出 `_play_actor()`（单国完整行动循环）与 `_cycle_parallel()`：
  - 并发时用 `ThreadPoolExecutor` 同时跑各国客户端（LLM 网络等待、规则 AI 规划、脚本客户端）；
  - **世界写入仍由 `session.lock` 逐条串行入账**，不并发改世界；单条命令仍是原子的；
  - 回执按 `turn_order()` 归并，`last_results` 与串行同序；
  - `before_actor()`（自动军令推进等）在并发开始前先串行执行一遍；
  - 回调（`emit/head/on_call/on_stream`）加锁串行，避免多个客户端输出行交织；`on_result` 本就在会话锁内调用；
  - 结算仍只调用一次 `resolve_turn()`，18 阶段与存档边界不变。
- 配置：`planning_workers`（顶部配置，默认 1）。`>1` 且无真人、无 `on_batch` 演出背压时启用并发；否则自动退回串行（真人输入与演出确认由主线程驱动，在工作线程里等待会死锁）。
- `tests/test_parallel_action.py` 用例：默认串行、并发确实重叠等待且回执按行动顺序归并、演出背压回退串行、并发周期可审计/可保存、配置校验。

## 冲突判定：只把可能互相干扰的国家串行

- 回合开始（行动期开始前）由军队域一次性判定"国家对"；判定使用当前态势与军令目标，随后各组内按行动顺序先跑行动开始前工作（自动军令推进）再行动：
  - 每国军队的**行动包络**＝现有位置 + 移动/进攻可达格（真实可达，不按玩家视野裁剪）+ 军令目标格；
  - 两国包络有交集 ⇒ 可能互相干扰（抢同一格、互相进攻、路径占位），必须按行动顺序**串行**；
  - 包络不相交 ⇒ 行动结果互不影响，可**并行**，因此不需要额外的观察时序隔离。
- 包络按周期缓存在军队域（`_envelope_cache`），同一回合内每国只遍历一次军队操作；冲突图用并查集分组，组内按 `turn_order` 串行、组间并行。
- 引擎侧契约：`Session.action_conflicts(actors)` 返回必须串行的国家对，默认空（无已知冲突）；`NativeSession` 覆盖为军队域判定。

## 没有做（明确边界）

- **判定标准就是"是否可能互相干扰"**：包络相交即视为可能干扰并串行；交战但本回合不可能接触的两国并行，结果等价，不另设战争图/宣战关系的分组口径。
- **真人 GUI 并发**：桌面宿主带 `on_batch`/`on_human`，当前一律串行；多 actor 演出队列与真人等待并行是后续工作。
- **确定性**：组内按 turn_order 固定；互不干扰的组之间不共享可变结果（市场报价按周期固定、库存延后到结算清算），所以组间写入顺序不影响结局。审计仍按真实入账顺序记录，可回放。
- 自动交易与外交拒签已从 `end_turn` 回执改到回合末统一执行（见[行动期与回合末结算](行动期与回合末结算-20261107.md)）：只与既有轮换次序有关，与谁先结束行动无关。

## 验证

- 全量 `python -m unittest discover -s tests -q`：1112 项通过、17 项跳过（新增并发/冲突/等价性用例）。
- 默认 `planning_workers=1` 时行为与原串行逐行同构（独立函数抽出，回执、回调、结算顺序不变）。
- 并发用例实测：三国、workers=2、客户端等待 0.25/0.05/0.05 秒 → 同时最多 2 个客户端在跑，墙钟明显短于串行之和，回执仍按行动顺序归并。

## 二次复检（2026-11-07）

- **组内行动前工作加锁**：`before_actor`（自动军令推进）会直接改世界，原先在并行组的工作线程里无锁调用；现在整段包在 `session.lock` 内，避免两个并行组同时推进。
- **可达结果按位置复用**：行动包络对同位置、同兵种、同速度的军队复用可达集合；实测 8 国 ×20 骑兵（160 支）第一遍约 0.17 秒，同回合缓存后接近 0，可接受。
- **军令目标计入包络**：已验证本回合军令目标格会进入包络（新周期缓存清空后判定生效）；缓存是"回合开始前一次性判定"，同周期后加军令不刷新。
- **串行/并行结果等价**：新增两项回归——无冲突三国跑 3 回合、相邻冲突对（宣战 + 贴脸军队）跑 2 回合，`workers=1` 与 `workers=2` 的归一化世界状态（资源、军队、建筑、领土、市场库存与报价、周期）完全一致；只有审计/日志的入账顺序可能不同。
- 已知小差异：并发下建筑/单位实例的编号分配顺序可能不同（属于记账顺序，不是结果差异）；`action_conflicts` 只能在行动期开始前调用。

## 2026-11-13 补充：真人 + LLM 的并行行动期

### 行为

- `planning_workers` 现在是三态：`0`/缺省=自动、`1`=强制串行、`>1`=显式并发（原语义）。
- 自动只对"单机一位真人 + 至少一个 LLM 席位"生效：真人在主线程等待输入，LLM/规则 AI 组在后台线程同时推进；世界写入、审计记录仍由 `session.lock` 串行，回执按 `turn_order` 归并，`before_settlement` 与结算仍只执行一次。
- 纯 AI 局默认串行（不自动并发）：并发会改变各国看到世界的先后，同一存档续跑不再可复现。需要"同时行动"的观战局可显式配置 `planning_workers: N`。
- 真人局 AI 侧不接收 `emit/head/on_call/on_stream/on_batch`：真人模式本就不展示外国思考，桌面演出由主线程独占。AI 动作的实际效果在回合末快照与结算中呈现。后台线程仍写审计，不再向真人推送外国私有调用。

### 实测（本机，2026-11-13）

- 规则 AI 八国局 6 回合：串行 5.99s；`workers=2` 7.29s；`workers=4` 7.42s。纯 Python 规划受 GIL 限制，并发反而更慢；且同一存档的后续状态与串行不同（同时决策改变了各自看到的先后）。**结论：纯 AI 局不自动并发。**
- LLM 席位价值在网络等待：离线替身（sleep）测试里，真人 0.15s + 两个 LLM 席位各 0.30s；串行 0.75s+，真人并行路径约 0.3s，墙钟约省一半，且回执仍按轮换次序归并。
- 新增回归：`tests/test_parallel_action.py` 覆盖真人 + LLM 重叠、`planning_workers=1` 强制串行、真人 + 规则席位保持串行、显式并发、审计串行化与边界可保存。

### 验证

- 引擎：`tests/test_parallel_action.py`（真人 + LLM 重叠、串行开关、审计串行化、边界可保存）与 `tests/test_desktop_parallel.py`（真实 `Controller` 协议：human_turn → submit end_turn → 演出 ack → 结算，离线替身 LLM 各 0.30s，真人回合在 0.6s 内返回并落盘）。全量 1118 项通过、17 项跳过。
- GUI：菜单自检 `MENU_SMOKE_OK`；本轮的整窗真人验收脚本因 Machine 环境重装后的合成指针/悬停时序多次抖动（早期 `MarketReady`、布局 hover 超时），未能在本轮跑完整条链。游戏 GUI 代码本轮未改（只改了验收脚本的等待/重试），上一轮 `HUMAN_GUI_OK` 仍覆盖界面本身；并发引擎路径由上述测试覆盖。

### 边界

- AI 后台线程的演出被抑制（不上屏），因此真人行动期间看不到 AI 的行军/战斗动画；这些效果在回合末统一结算时呈现。若要让 AI 动作在真人行动期间也逐条演出，需要给桌面端做多 actor 演出队列（后续）。
- 多真人席位仍串行；联机 M2 未开始。
