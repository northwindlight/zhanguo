# 候选 FFN 开关复核

2026-11-09 用户询问为什么没有使用 FFN、是否会限制能力。

当前模型的两个上下文 Transformer Block 都有 `160→640→160` 的 GELU FFN；
上下文/候选嵌入和评分头也有非线性 MLP。关闭的是候选交互后的额外 `cand_ffn`，
不能说整个模型没有 FFN。14 世界 BC 启动脚本显式 `cand_ffn=False`，没有传
`--cand-ffn`，后续 PPO 沿用该 checkpoint 配置；默认关闭也保留旧权重兼容。
交接报告记载旧 FFN 版实局 70.9%、验证 loss1.43，不能作为启用后必然更好的
证据，也不是足够严格的容量消融。

## 开关实际行为与新发现

`model.py` 中 `ffn1/ffn2` 实际实例化两个完整 `Block`，含自注意力与 FFN，
不是两个纯逐候选 FFN。以当前宽度、深度和 critic/族头配置计，参数从
1,037,607 增到 1,450,727，增加约 40%；还会额外引入两次候选自注意力。

现有 forward 调用 `ffn1(h)` / `ffn2(h)` 没传候选 padding mask，而 `Block`
内部的自注意力在 mask=None 时会把补齐行作为 K/V。虽然最终动作分数屏蔽了
padding，有效候选此前已受到补齐行影响。

合成随机初始化检查，CPU Torch2.14.1、seed17、width32/depth1/heads4，
同一份 3 候选输入分别单独前向、与 29 候选样本组批：

| 开关 | 有效候选最大 logit 差 | 动作概率最大差 |
| --- | ---: | ---: |
| cand_ffn=False | 0 | 0 |
| cand_ffn=True | 0.03154254 | 0.01001608 |

证据与复现脚本：`archive/previews/candidate-ffn-audit-20261109/`。
这是合成输入的批处理一致性检查，不能把约 1 个百分点的变化说成正式对局收益，
也不能据此断言旧 FFN 版 70.9% 的全部原因。当前在线模型未启用额外块，未受这条
路径影响。本轮未修改网络 forward、在跑权重、训练数据或推理缓存。

## 能力判断

在两组已测环境中，PPO 第 10 轮总 S 为教师的104.03%/114.03%，说明该学习路线
可以在这些场景的总 S 上超越启发式教师。逐席、尾段和跨环境稳定性仍需提升。

额外 FFN 可以增加候选状态交互后的非线性处理深度，但尚未证明它是当前成绩的
主要瓶颈。后续比较应先处理 padding 一致性，区分纯残差 FFN 与完整额外注意力
块，以相同初始化、数据、训练预算及逐席长局评测衡量收益；不能只看 BC loss。
