# 动态回合：实现层研究与方案

记录日期：2026-11-07。状态：**研究记录与建议，未实施**；方向与边界仍以 [动态回合与联机调度](动态回合与联机调度.md)（2026-10-28）为准。

## 一句话结论

动态回合的机制门槛比预期低（引擎的写权限早已与调度解耦，写操作按动作原子加锁），真正的难点是**语义**：并行期间"谁先谁后、各自能看到什么"。`stock` 分支验证的路线是"**等待重叠、世界变更串行入账**"（提交 `39dee52`），不是并发改世界；native 可以沿用这条路线先拿到混合局的实际收益，但战争顺序、共享冲突与信息时序必须先在规则层定义，不能靠线程池冒充已完成。

## 1. 问题分两层

| 层次 | 内容 | 语义是否改变 | 主要收益 |
| --- | --- | --- | --- |
| A 并发等待 | 各国客户端（LLM 网络往返、真人思考）同时进行，世界写操作仍逐条串行入账 | 基本不变（写顺序可能由锁到达顺序决定，见 §4） | 墙钟从"各国之和"降到"最慢一国 + 收尾" |
| B 并发行动 | 多国同时作用于同一世界，需要冲突仲裁与信息时序规则 | 会改变（先手、视野、成交先后） | 真正的同时行动体验；联机必需 |

先把 A 做对，B 才有的谈。现有设计文档里"和平并行／战争有序／统一结算"属于 B；A 是 B 的机制底座。

## 2. 现状事实（代码级）

### 2.1 串行只发生在调度循环，不在规则层

- `engine/session.py:387-435`：`cycle()` 逐个 `for actor in self.turn_order()`，每个 actor 跑完整的 `client.play()`，全部结束后 `self.world.resolve_turn()`。
- `turn_order()`（`engine/session.py:124-136`）按回合数轮转先手，注释明确是为了避免固定名单顺序带来"每回合同一国先动手"的先手优势。
- 每个 actor 的等待是阻塞的：LLM 是完整 agentic 循环（`clients/llm.py:213-318`，默认最多 28 个模型往返）；真人是 `ui/desktop.py:268-284` 的 `human_turn()`，等 GUI 输入直到本国 `can_act` 为假。

### 2.2 写权限早已与"轮到谁"解耦

- 行动门只解析"本国未结束"：`native:government.can_act` = 存活且不在本期末态集合（`mods/native/government/objects.py:84`）；`engine/runtime.py:1143-1148` 只校验 `world.phase == '行动'` 加这道门。
- `BoundPlayer.submit`（`engine/api.py:66-106`）只校验 actor 是否仍在名单、控制代次是否一致，不校验"是否轮到"。
- 结论：**行动期内多个 actor 可以并发提交，引擎本身不阻止**；串行是 `cycle()` 的调度约定，不是权限。这是 native 能直接借用 stock 结构的关键。

### 2.3 单次动作是原子的，但"动作之间的顺序"不确定

- 所有写都经 `PlayerSession`/`BoundPlayer`，在 `session.lock`（RLock）内执行（`engine/api.py:66-106`、`engine/player.py:139-178`、`engine/session.py:297`）。
- 审计与回调也在同一把锁内追加（`engine/session.py:361-376`）。
- 并发后**单条命令不会互相撕裂**，但"先买还是先卖"取决于抢锁顺序，也就是线程调度顺序。

### 2.4 结算与调度无关

`runtime.settle`（`engine/runtime.py:1008`）按阶段依赖的拓扑序执行，`world.phase` 守卫重入，每个周期只调用一次（`engine/session.py:419`）。18 阶段顺序、参与者遍历、战斗掷骰都在这里；动态回合只改"行动期怎么排"，不需要改结算。

### 2.5 行动期里哪些动作对顺序敏感

| 动作 | 生效时机 | 并发后果 |
| --- | --- | --- |
| 市场买卖 | 立即：`_trade` 当场扣共享库存、记本期流量（`mods/native/market/objects.py:241-257`） | 报价按本期参考价固定、不随他人成交波动（`:176-210`，这是并发友好的既有设计），但库存售罄是先到先得 |
| 占地/建站 | 立即：`territory.create/create_claim/claim` 拒绝已被占（`mods/native/territory/objects.py:98-136`） | 同一无主地两人同抢，先到者得 |
| 军队移动 | 该国行动开始时由 `before_actor` 推进自动军令并立即 `move_many/attack`（`mods/native/session.py:97-104`、`mods/native/army/march_orders.py:114-159`） | 移动顺序决定占位/阻挡，先到先得 |
| 战斗 | 延后到结算阶段同时掷骰（`mods/native/army/mod.py:39-43`） | 天然并发友好，已不是问题 |
| 外交/间谍 | 命令入队，结算阶段生效（`docs/design/动态回合与联机调度.md`） | 并发友好 |
| 期末动作 | `end_turn` 立即跑自动交易与外交拒绝（`mods/native/session.py:21-38`）；建设/征兵订单在 cycle 开头按名单串行推进（`mods/native/session.py:72-95`） | 谁先结束谁先改市场；订单推进相位需要重新定义 |
| 地图知识 | 每次写后 `capture_maps`，只有结算后 `publish_maps`（`mods/native/session.py:93-94,106-110`） | 中期只更新本国视野；对外"测绘版本"仍是期末发布，天然有边界 |

### 2.6 存档只看完整边界

`to_save()` 要求 `_boundary` 且 `world.phase == '行动'`（`engine/session.py:437-439`），native 还拒绝"已行动过又保存"（`mods/native/session.py:55-60`）。动态回合下"部分玩家已就绪"会成为常态，现有契约没有就绪集合的位置。

### 2.7 演出与 GUI 假设单线程、单观众

- `ui/desktop.py:224` 注释写明真人命令"Run on the sole session thread"；输入线程只入队。
- 演出是单条 timeline + `playback_ack` 背压（`ui/desktop.py:286-323`），宿主在 `on_batch` 里等确认；一个 actor 的演出会阻塞整个 cycle。
- 单机只支持一位真人 viewer（`ui/desktop.py:272`）。
- 并行后需要：按 actor 隔离的演出队列与确认、多 actor 状态显示、真人等待与 AI 等待同时进行。

### 2.8 已经具备、可直接复用的资产

- 真人请求协议：`request_id` + `seat_token` + `period` + `control_generation`，重复请求返回同一结果（`ui/desktop.py:246-262`）——这正是联机重发/去重需要的。
- 控制代次 `generation`：控制权变更后旧句柄命令被拒（`engine/session.py:313-314`、`engine/api.py:29-40`）。
- 审计日志与档案分段、串行对照可重放（`engine/session.py:437-476`）。
- stock 的调度骨架与三个并发测试（见 §3）。

## 3. stock 参考实现

`origin/stock`（最新；设计文档记录的快照为 `0fa86f63`）`mods/stock/session.py`：

- `_cycle_parallel`（`:88-124`）：`ThreadPoolExecutor(max_workers=min(len(actors), workers))`，每个 actor 交给 `_plan_one` 跑完整规划循环；线程池退出后**只调用一次** `world.resolve_turn()`。
- `_plan_one`（`:63-86`）：与引擎串行循环同构（含控制代次转移，最多 8 次），只是搬进工作线程。
- `_guard`（`:54-61`）：把 `emit/head/on_call/on_stream` 包上会话锁再回调，保证不同玩家的输出行不交织、不与入账互锁。
- 世界变更：全部经 `BoundPlayer`，由会话锁逐条串行入账（docstring `:91-93`：并发只重叠模型网络等待，不重叠世界变更）；回执按 `turn_order` 归并，`last_results` 与串行一致。
- `planning_workers=1` 退回 `super().cycle()` 严格串行（`:126-134`）；配置与发行版开关分离。
- 边界：`validate_boundary` 仍然要求所有 actor 都结束才可保存（`:215-218`）。

**对 native 明确不够的地方**：没有 `on_batch`/`on_human`（stock 无真人、无演出背压）；写顺序不确定（回执归并顺序 ≠ 执行顺序）；没有战争图/共享库存/迷雾的仲裁规则；没有多连接、超时与重连。

## 4. 难点排序（为什么"套线程池"不是完成）

1. **语义仲裁（最重）**：并行后同一期的市场库存、无主地、军队占位、自动交易谁先？今天由"整国轮流"隐含定义；并行后必须显式定义并写成规则，否则结果由线程调度决定。
2. **观察时序**：并行期间 A 观察时可能看到 B 的半成品行动。实时读会奖励"手快"、也会泄露"某人正在行动"；期初快照读则公平但需要世界快照/视图冻结，且与"行动期立即生效"的现有契约冲突。这是**规则与产品决策**，不是代码决策。
3. **确定性/可重放**：审计顺序就是执行顺序；并发后同输入可能不同结局。要么接受"审计即正典"（可重放不可复现），要么引入确定性仲裁（提交序号/令牌/固定批次），后者要写进存档与审计格式。
4. **存档与断线**：动态回合必然出现"部分就绪、部分在行动"。要么只允许期初重来（会丢进度），要么设计就绪集合、超时托管与重连恢复。
5. **演出/GUI**：单 timeline、单 viewer、单 session 线程的假设要拆；多 actor 演出、并行进度显示、真人输入与 AI 等待同时进行。
6. **联机**：权威宿主、连接令牌、超时、防重复结算；现有 request_id/generation 是基础，但多连接归属未设计。

## 5. 方案空间

| 方案 | 机制 | 语义变化 | 成本 | 主要风险 |
| --- | --- | --- | --- | --- |
| S0 并发等待、串行入账 | 多国 `play()` 并发；写仍由会话锁逐条入账 | 写顺序变为到达顺序；观察可看到他人中期动作 | 中（调度层 + 回调/演出隔离 + GUI 多 actor） | 顺序不确定；信息时序未定义 |
| S1 并发等待、确定性写序 | S0 + 写入令牌/提交序号，按固定规则排序入账 | 每期动作顺序可重放；与"整国轮流"不同 | 中（令牌 + 审计格式 + 冲突规则） | 规则层要拍板每类冲突 |
| S2 期初快照、期末合并 | 各国在期初快照上规划，提交计划；期末按规则合并执行 | 最接近文明式同时行动 | 大（多数即时动作改规划-提交两段；视图冻结） | 规则域重构，周期长 |
| S3 实时竞争 | 完全实时、谁先到谁赢 | 大 | 中 | 快者通吃、迷雾泄露、不可重放，不建议 |

**建议先 S0，再 S1；S2 只在明确要"标准同时行动"语义时再做。**

## 6. 分阶段建议

**M0（混合局收益，最先做）**：并发等待、写串行。
- 单人混合局（1 真人 + N 规则/LLM）最大受益：真人不必等 AI 逐个走完，AI 之间也不必排队。
- 机制：`engine/session.py` 的 `cycle()` 抽一层调度器；默认保留现有串行实现作为对照；并发实现参考 stock `_cycle_parallel`。
- 必须同时处理：`_callbacks/_emit` 的线程安全（每个回调只允许在单一队列线程执行）；`on_batch` 演出不能跨 actor 阻塞（按 actor 排队）；`turn_order` 回执归并保持。
- 语义：接受"写顺序=到达顺序"，但需在文档与 GUI 明示；不宣称已完成动态回合。

**M1（冲突串行，已按"是否可能互相干扰"实现）**：不设战争图/宣战关系分组；回合开始前算各国的行动包络，包络相交的国家对串行、其余并行。市场报价按周期固定、库存延后到结算，因此互不干扰的组之间不共享可变结果，组间写入顺序不影响结局。见下节实现进展。

**M2（联机）**：M1 之后接权威宿主、连接与断线恢复；动态回合是联机前置条件，不能等联机时再补。

## 7. 最小验证原型（离线、不调模型）

不改产品入口，先做一个可回退的实验分支：

1. `engine/session.py`：把 `cycle()` 的循环体抽成 `_play_actor(actor)`，新增 `cycle(..., scheduler=...)`；默认 `SerialScheduler` 保持现有行为（全量回归的基准）。
2. `ParallelScheduler`：`ThreadPoolExecutor` 并发 `_play_actor`；回调经单线程队列串行；回执按 `turn_order` 归并。
3. 模拟客户端（不调模型）：脚本化"读 → 睡 → 写"序列，用 barrier/Event 控制交错；跑 8 个 actor。
4. 验收：
   - 等待确实重叠（墙钟 < 串行之和，且等于最慢者 + 收尾）；
   - 审计可完整回放；同脚本串行与并发逐动作对照，输出"对顺序敏感的动作"实测清单（这是最有价值的产出，能校准 §2.5 的判断）；
   - 无锁死、无重入、控制代次与真人请求幂等不变；
   - `planning_workers=1` 等价于现有串行（对齐 stock 的回退测试）。
5. 之后再动 GUI（多 actor 状态、按 actor 演出队列），最后才是真人/联机。

## 9. 风险清单

- 把"锁住不撕裂"当成"语义正确"：锁只保证单动作原子，不定义顺序，也不定义冲突。
- LLM 客户端的进程内共享状态（`clients/context.py:224` 的 `_HIT_HIST` 等模块级统计）在并发下需要复查；provider/后端按客户端实例持有，跨 actor 并发基本安全，但要写测试固定。
- `capture_maps` 在每次写后对全部 owner 采样，8 国并发时是明显的 CPU 热点（`mods/native/session.py:106-110`），M0 前应先测量。
- 演出背压会跨 actor 阻塞工作线程，必须按 actor 拆队列，否则并发收益被 GUI 吃掉。
- 存档格式与依赖校验：就绪集合/调度状态一旦入库要走严格依赖检查，旧档需拒绝或迁移。
- 调度不使用战争图/宣战关系，只按行动包络判定"是否可能互相干扰"，因此不需要处理宣战在结算才生效的时点问题。

## 2026-11-07 实现进展

M0（并发等待）已落地：引擎抽出 `Session._play_actor / _cycle_parallel`，顶层配置 `planning_workers > 1` 启用并发等待；世界写入仍由会话锁逐条串行入账、回执按 `turn_order` 归并、结算仍一次；真人出席或带演出背压（`on_batch`）时自动退回串行。见[并发行动期记录](../reviews/并发行动期-20261107.md)。

M1 部分落地（冲突判定）：回合开始后由军队域计算各国的"行动包络"（现有位置＋移动/进攻可达＋军令目标，按周期缓存），包络相交的两国按行动顺序串行、其余并行。这解决了本方案的 D1（观察时序）：不能互相干扰的国家并行时，读到对方中间状态也不影响结果；能干扰的国家顺序执行，观察顺序与串行一致。

判定标准就是"是否可能互相干扰"：行动包络相交的国家串行，其余并行；不另设战争图/宣战关系口径，互不干扰的组之间不共享可变结果，组间写入顺序不影响结局。仍未做：真人 GUI 并发与多 actor 演出、M2 联机。
