## 一、要达到什么

让规则有明确契约，模块按事拥有对象与行为，各种玩家通过同一套动作和事实接口参与游戏。改一项规则时，可以找到它的负责模块，判断影响，并验证结果。

已有方向以 [模块化口径](../design/模块化口径.md)、[对象化口径](../design/对象化口径.md) 和 [正规化口径定稿](../design/正规化口径定稿.md) 为准。本大纲规定推进顺序和审阅停点，不重定玩法，也不宣布现有实现已经符合全部口径。

近期目标是完成一个可推广的 army 样板，再决定其他域的展开方式。远期路线记录在这里，近期实现范围仍收窄。

## 二、怎么推进

1. 每阶段开始前，写清现状、问题、拟改边界、行为影响和验收场景，供用户审阅。
2. 一个批次只处理一个可以独立解释的问题；规则变化与代码组织变化分别说明。
3. 先保留可运行的过渡接口，再逐项迁移；兼容接口必须记录消费者和删除条件。
4. 每阶段交付改动说明、实际验证结果、残留问题和下一步建议，停在该阶段，由用户决定是否继续。
5. 已确定的规则不借重构重新解释；遇到未定案或相互冲突的口径，先登记案例，裁决后实现。
6. 代码量、文件数、依赖清单只作诊断。评价收益看责任是否清楚、旧路径是否退出、修改是否局部、客户端行为是否一致。
7. 性能不设验收门槛，不安排专门优化阶段；实现应保持能运行和能完成验证。
8. 测试使用临时目录与合成存档；真实 `mp_save.json` 不进入改造验证。

## 三、阶段 A：收尾当前实现，固定行为基线

**目的：先把现有样板补可靠，建立后面重构能依赖的基线。**

待处理问题均来自本次审阅复现，实施时补入可重复的验收场景：

- 调动到未物化野地后，玩家状态查询不能因 `tiles` 缺键崩溃；位置与土地归属继续分开。
- 工具入口与直接动作入口的阶段裁决不同：先选定一项军事动作，打通两条入口，验证统一裁决方案；其他动作在阶段 B 展开。
- 定义状态版本代表什么、哪些可观察变化使版本更新，并验证移动后的版本与查询一致。
- `Unit.move_to` 等多字段行为先完整校验，再变更；非法参数失败后保留原状态。
- 存档中的国家编码、番号、gid 与计数器进行一致性校验，损坏数据在加载时明确拒绝。

**交付：** 小范围修复、行为契约、补充场景与现有回归结果。沿用既有规则，不扩大对象化范围。

**验收：** 合法的野地调动可继续查询；失败动作不留下非契约副作用；查询版本反映已定义的变化；临时存档往返与续跑结果符合契约。

**停点：** 用户审阅修复及入口方案，再决定是否展开阶段 B。

## 四、阶段 B：统一玩家动作与事实接口

**目的：LLM、规则 AI、未来人类 GUI 共用规则裁决，客户端只负责表达和决策。**

- 盘点公开动作、别名、直接 World 调用和规则 AI 的内部查询；初始化、观海管理与玩家操作分别界定权限。
- 明确唯一的玩家动作入口。阶段、身份、政体、视野和额度等裁决有明确负责位置，各种适配最终进入相同规则路径。
- 对动作结果定义共享结构：是否接受、是否生效、失败原因、变化与待处理效果。文本回执由共享结果生成；按动作逐项落地，不一次重写全部工具。
- 完善结构化玩家事实接口，包含当前事实、可见变化、待办和结果。查询不能返回可修改的内部状态或泄漏迷雾信息。
- 给规则 AI 提供必要的公开查询，例如合法行动目标；逐项替换私有方法和内部字段读取，不为冻结版本永久保留旧路径。
- 事实生成与文字/图片呈现分开，共享权限过滤；保留现有历史回放与缓存语义。

**交付：** 玩家 API 契约、消费者迁移清单，以及每批动作的接入结果。

**验收：** 同一玩家、同一状态、同一意图，经不同客户端得到相同裁决和世界变化；非行动阶段、政体禁用、迷雾目标、部分失败与延迟生效均有场景验证。

**停点：** 用户审阅接口及客户端接入情况，确认再继续 army 的领域边界整理。

## 五、阶段 C：把 army 做成完整样板

**目的：从“一个受保护的集合”推进到“有清楚边界的军事领域”。**

- 固定 `Unit / Units` 的字段、不变量、行为与公开读取方式。兵种参数仍是声明式数值表。
- 域内改动逐步使用行为方法；字典/列表兼容仅服务登记过的旧调用点，逐项减少并删除。
- 盘点 army 的跨域需求，按实际业务收成窄接口：地形与通行事实、建筑防御、资源账户、外交关系、事件记录等。具体接口通过调用案例确定，不先堆一个万能服务。
- 界定占领、核心归还、亡国、强制休战和清理的责任。军队报告战斗与占领结果，各域通过明确协作完成自己负责的变化。
- 地形、建筑、账户等尚未对象化时，可以先由其所属域提供小接口；不要求为完成 army 一次改完其他域。
- 收缩 `method._*` 依赖和按裸键写入的 Requests；缓存保持域内派生量。
- 检查运行时权限包装、兼容转口是否仍有必要；已有机制随旧路径退出而简化，不另加通用框架。

**交付：** army 责任表、公开接口表、依赖变化、兼容删除清单与行为验证。

**验收：** 跨域修改经过拥有者的行为接口；军队规则不依赖其他域的私有方法；移动/进攻/撤退/补给/阵亡及其存档恢复符合规则。对选定的小实现做替换验证，明确替换范围与仍存限制。

**停点：** 用户判断样板收益是否足够，再决定是否向其他域推广。不得仅凭 `Owns = ["units"]` 宣布样板完成。

## 六、阶段 D 及以后：待样板验收后逐域展开

以下是后续方向，未授权实施；每项都先补具体方案，再开始改动。

| 顺序 | 范围 | 要厘清的边界 | 难度 |
|---|---|---|---|
| D1 | 地块与领土 | 地形/资源事实、物化、归属、核心领土；生成与渲染的责任 | 中 |
| D2 | 建筑与工程 | 在建/落成、槽位、生产与防御查询；变化与结算阶段 | 中 |
| D3 | 国家与资源账户 | 身份、资源、预留、扣费、退款、账本；国家生命周期与玩家记忆分开 | 高 |
| D4 | 条约与联盟 | 外交实体、条约、战争、议案、投票、排队命令；失效与恢复 | 高 |
| D5 | 市场、央行、地图生成 | 各自独立的规则与状态；依赖前面已稳定的账户/事实接口 | 中高 |
| D6 | 发行版与模块替换验收 | 精简全局转口；验证替换、摘除、缺依赖报错和存档环境契约 | 高 |

government 随上述责任迁移逐步收缩。回合生命周期、存档装配和客户端记忆的归属，分别依据实际需求裁决，不将整个杂项桶再包装成一个大对象。

存档变化按阶段制定协议：当前环境内的往返与续跑可复现；是否支持跨版本迁移、哪些声明变化必须拒绝加载，另作明确裁决。不得默默放宽当前严格依赖检查。

## 七、共同验收与暂缓范围

每个实施批次至少说明：解决了什么、规则是否变化、消费者是否全部迁移、验证覆盖什么、还留下什么过渡接口。验证优先覆盖真实行为边界，再按影响范围跑回归；全量通过不能替代缺失场景。

暂缓全面对象化、完整 GUI、美术、新玩法、第三方插件生态，以及新增通用事务/事件/注入框架。现有实现遇到具体问题时先作局部判断，不预先规定一次重写运行时。

推进顺序固定为：**当前修复基线 → 玩家接口 → army 完整样板 → 用户决定推广 → 逐域改造与替换验收**。不承诺一周完成全部改造，不用日期压缩审阅与验收。
