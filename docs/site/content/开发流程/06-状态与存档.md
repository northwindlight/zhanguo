# 状态与存档

## 状态归谁

每个状态键在某个模块的 `[State] Owns` 里声明，只有一个所有者。键名要短而具体（`bank`、`territory`、`buildings`），不要用 `data`、`state` 这种迟早会撞名的名字。发行版的 `RequiredState` 列出必须有人拥有的键，缺了在装载时报 `state 无主`。

## 存取

```python
def save_state(self, world):
    return world.bank.to_save()

def load_state(self, world, state):
    world.bank.restore(state)
```

- `save_state` 只返回能 JSON 序列化的纯数据（dict、list、标量），不要返回对象引用、生成器或 dataclass 实例。
- `load_state` 要校验输入，拒绝不认识的数据。基类的缺省实现遇到非空状态会抛 `ModError`，所以有状态的模块必须实现它。
- `save → load → save` 必须得到完全相同的结果。

## 依赖清单

整局存档（格式 `zhanguo.session/5`）记录完整的依赖清单：发行版全部字段，每个模块的 Id、版本、依赖和声明原文，阶段契约，状态所有者，全部工具的 JSON Schema，面板清单，内容注册表。读档时用 `runtime.check_save_dependencies(manifest)` 核对，任何一项不同都拒绝装载：

```
存档 Mod 依赖/版本/工具契约与当前加载环境不相同，拒绝加载
```

这是刻意的：1.0 之前不承诺旧档兼容，宁可拒绝，也不加载出一个半对半错的世界。读档失败时宿主丢弃候选世界，不会替换当前世界。

## 什么时候必须升版本

模块的声明、状态格式、工具 schema、阶段契约、内容定义或依赖关系变了，就提升 `[Mod] Version`。只改内部实现、对外接口不变时不必升。

新增内容同样会改变依赖清单：给发行版加一种资源或兵种后，旧档会被拒绝，因为旧档里没有新内容的库存或部队。

## 升级旧档

确实需要沿用旧档时，用脚本生成**新文件**，不要在 `load_state` 里悄悄兼容：

```bash
# 只刷新依赖清单（领域状态格式不变的情况）；不给 --output 时原地写并先留备份
python3 scripts/upgrade_save_manifest.py --config <配置> --save <旧存档> --output <新存档>
# native／experimental 已知版本的校验后升级，原档与相邻审计历史保留
python3 scripts/upgrade_native_save.py --config <原局配置> --input <旧存档> --output <新存档>
```

两个脚本只认识列出的已知版本，未知清单和混用发行版的存档一律拒绝。桌面版的存档列表也提供“升级为新副本”，真实对局不会被自动迁移。

## 存档时机

只能在行动边界存档，回合进行到一半会报 `Save only at an action boundary`。存档与当前配置的场景不同，则报 `Scenario differs from saved scenario`。

## 往返测试

带状态的模块都要有这一条：

```python
def test_state_round_trip(self):
    host = GameHost.new(self.cfg())
    host.cycle()
    path = Path(self.tmp) / 'save.json'
    host.save(path)
    self.assertEqual(GameHost.load(path, self.cfg()).to_save(), host.to_save())
```

`to_save()` 完全相等才算通过。这比“读回来还能跑”严格得多，能抓住引用共享、时间戳、浮点精度这类问题。
