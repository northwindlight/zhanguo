# 暴露给玩家

模型、规则 AI 和真人桌面版走的是同一套玩家接口：模型看到的工具表与回执，就是它对你的规则了解到的全部。所以工具名、参数和描述写得好不好，不只是接口问题，也决定了模型能不能玩对。

## 两种工具

| 类型 | 标记 | 作用 |
| --- | --- | --- |
| 动作 | `read_only=False`（缺省） | 改世界：建造、征兵、移动、交易、外交提交 |
| 只读查询 | `read_only=True` | 看世界：地块、部队、库存、外交、报表 |

只读工具不受「只能在行动阶段提交」的限制。其中被选为**事实**的那些，每回合自动随状态发给玩家，不必再查。

## 路径一：模块直接返回工具

小型发行版（`hello`、minigame）由模块的 `tools()` 直接返回 `Tool`。事实由发行版的 `PlayerState` 列出：

```toml
[Distribution]
PlayerState = ["nations", "government", "land", "view", "army", "diplomacy", "stock", "catalog", "news"]
PlayerEvents = "news"
```

`PlayerState` 里每一项都必须是已注册的只读工具，否则装载时报 `玩家状态必须声明唯一的只读工具`；`PlayerEvents` 同理。

## 路径二：玩家 API＋发行版工具层

native 系发行版的规则模块不直接定义工具。模块声明自己对玩家开放哪些方法：

```toml
# mods/native/bank/mod.toml
[PlayerAPI]
Methods = ["borrow", "position", "buy_report"]
ReadOnly = ["position"]
```

```python
# mods/native/bank/api.py —— 只做转发，规则在领域对象里
class BankAPI:
    def __init__(self, world):
        self.world = world
    def borrow(self, actor):
        ...
    def position(self, actor):
        return self.world.bank.position(actor)
    def buy_report(self, actor, target, turn=None):
        return self.world.bank.buy_report(actor, target, turn)

# mods/native/bank/mod.py
def player_api(self, world):
    return BankAPI(world)
```

发行版的工具层（`[Distribution.Tools] Entry = "mods.native.tools:build"`）负责工具名、参数结构、描述和回执文案，并通过 `runtime.player_api(world, 能力名)` 调用模块：

```python
# mods/native/tools/bank.py（节选）
def tools(runtime):
    def bank(world, actor):
        return runtime.player_api(world, 'economy:bank').position(actor)
    def buy_report(world, actor, target: str, turn: int | None = None):
        return runtime.player_api(world, 'economy:bank').buy_report(actor, target, turn)
    return (
        Tool('bank', bank, owner='economy:bank', api=('position',),
             read_only=True, fact=True, panel=True, description='本国现金、信用额度、负债与贷款剩余；无需参数。'),
        Action('buy_report', buy_report, owner='economy:bank', api=('buy_report',), description='……'),
    )
```

装载时引擎核对两边：

- 工具的 `owner` 能力必须有提供者，且那个模块声明了 `[PlayerAPI]`；
- 工具引用的 `api` 方法必须在 `Methods` 里，读写性质也要一致：只读工具不能覆盖写方法，反过来也不行；
- `[PlayerAPI]` 的每个方法都必须被某个工具或动作封装，否则报 `[PlayerAPI] 方法未封装`；
- `fact=True` 或 `panel=True` 的工具必须只读。

这条路径下，事实缺省取所有 `fact=True` 的工具，发行版可以用 `PlayerStateInclude`／`PlayerStateExclude` 微调。`ReadOnlyPanel = "query"` 把模型侧的只读面板收拢到一个分发工具，其余只读工具照样注册，但不进模型工具表。`Action` 是工具层内部的动作适配，不会作为单独的工具出现在模型工具表里；native 用 `commands.wrap` 把同领域的动作归并成 `military`、`economy` 这类组合工具。

为什么要分两层：规则模块因此不带任何提示词或展示格式，换一套措辞、语言或工具粒度只改工具层；真人桌面版和规则 AI 也直接复用同一套玩家 API，不用另写一套门槛或公式。

## 描述就是说明书

`description` 原样进入模型工具表。写描述时自查：

- 参数是什么、什么格式（坐标从 0 开始？用地名还是编号？）；
- 有什么前置条件（必须是本国地块？必须先有兵营？）；
- 会怎样失败（材料不足？本格本回合已经动工？）；
- 做决定前该先查哪里（价格看报价，战况看面板）。

失败时，在回执的 `data` 里给出原因字段（如 `reason`、`required`、`available`），呈现层据此写出可操作的提示，模型也能据此调整，而不是反复重试同一个调用。

## 内容键值与别名

资源、建筑、兵种、地形注册成**内容**之后，玩家可以写短键（`farm`）、完整 ID（`native:farm`）或显示名。工具参数声明 `content_parameters` 后，引擎会在调用前归一化：

```python
Tool('build', self._build, parameters={...}, content_parameters=('kind',))
```

再注册一组别名，模型照抄面板上的中文名也能直接提交：

```python
self.runtime.content.register_aliases('mini:buildings', {'农场': 'mini:farm'})
```

认不出的键值返回 `未知内容键值：…`；短键在多个命名空间里重名时返回 `键值冲突，请指定命名空间`。

## 结束回合的契约

模型客户端在 `end_turn` 成功后，从回执里取 `data['text']` 记作本回合小结。所以发行版的 `end_turn` 必须接受 `summary` 参数，并在回执数据里返回 `text`：

```python
@staticmethod
def _end_turn(world, actor, summary: str = ''):
    result = world.government.end_turn(actor)
    return {**result, 'text': summary or f'第 {result["period"]} 期行动结束。'}
```

漏了 `text`，模型客户端会在回合末直接报错。

## 引擎保留的玩家工具

`player_state`、`player_rules`、`player_events`、`memory_search` 由引擎和客户端提供，模块工具不能占用这些名字。

## 自查

1. 只看工具表和状态，能猜出每个参数该填什么吗？
2. 每种失败的原因，回执里都说清了吗？
3. 每回合的事实够判断局势吗？发行版没有的概念，简报就不出现那一节，不会用 0 冒充“没有”。
4. `end_turn` 接受 `summary`、返回 `text` 了吗？
